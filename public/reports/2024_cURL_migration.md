# 移行計画レポート — cURL

## 1. 移行難易度評価

**工数見積もり: S（移行の必要性はほぼない）**

cURLはその分野において他の追随を許さない完成度です。「移行」より「継続的なバージョンアップ」と「適切な使い方」が最適な戦略です。

---

## 2. 移行戦略の選択肢

| 戦略 | 概要 | メリット | デメリット | 推奨度 |
|---|---|---|---|---|
| cURL継続・バージョンアップ | 最新版への追従 | 安定・実績 | なし | ⭐⭐⭐⭐⭐ |
| reqwest（Rust） | Rustのcurl代替 | 型安全・async対応 | cURLほどのプロトコル対応なし | ⭐⭐⭐ |
| httpx（Python） | Pythonからの利用 | 使いやすいAPI | パフォーマンス低下 | ⭐⭐⭐ |
| nativeの fetch API | ブラウザ/Node.js | 標準API | 一部機能不足 | ⭐⭐⭐ |

---

## 3. フェーズ別移行ロードマップ

**cURLの移行は推奨しません。** 必要に応じた言語別のラッパーライブラリ活用が最善です。

- **Phase 1（即時）**: 最新cURLへのアップグレード
- **Phase 2（随時）**: 言語別libcurlバインディングの最新化
- **Phase 3（必要時のみ）**: HTTP/3（QUIC）対応の確認と有効化

---

## 4. 推奨アプローチ

| 言語 | 推奨ライブラリ | 備考 |
|---|---|---|
| C/C++ | libcurl（直接） | 最高性能 |
| Python | requests / httpx | libcurlラッパー |
| Go | net/http | 標準ライブラリで十分 |
| Rust | reqwest / curl-rust | reqwestはhyperベース |
| Node.js | node-libcurl | libcurlバインディング |

---

## 5. 移行コスト概算

| 作業 | 難易度 | 人月 | 優先度 |
|---|---|---|---|
| バージョンアップ | 低 | 0.1 | 高（定期実施） |
| HTTP/3対応 | 低 | 0.5 | 中 |
| 言語バインディング更新 | 低 | 0.5 | 中 |

**cURLは移行コストがほぼゼロの理想的なライブラリです。現状維持を強く推奨します。**
